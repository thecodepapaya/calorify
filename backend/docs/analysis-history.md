# Meal-analysis history page

This is the canonical design and operational reference for the read-only
inspector at `GET /analysis-history`. It reconstructs text and image analyses
from durable application data and bounded structured observations rather than
requiring operators to correlate process logs manually.

## Architecture and retained data

The page is server-rendered by the existing Fastify backend. It does not add a
separate frontend deployment. `meal_analysis_session` remains the source of
truth for durable checkpoints. The inspector joins its clarification,
meal-type, feedback, correction, and mirrored meal-log audit records.

Append-only `meal_analysis_observation` rows record each initial analysis,
clarification, resume, meal-type continuation, and reanalysis pass. Each row
contains streamed event order with elapsed offsets, a bounded timing summary,
provider attempts, and allow-listed artifacts captured at decision boundaries:

- validated structured decomposition;
- selected USDA match or explicit unmatched/deterministic/fallback decision;
- presentation input; and
- presentation output.

The latest exact streamed response is stored separately on the session because
persisted `result_data` is not identical to every wire outcome, notably
no-food and error events. Rows created before exact-response capture fall back
to the legacy persisted result and are labelled accordingly.

Image requests persist only the object key. Rendering reconstructs a viewable
URL through the existing Oracle read-URL builder; the upload credential is
never retained in inspector data.

## Access

The route returns `404` until `ANALYSIS_HISTORY_PASSWORD` is set in the target
server's ignored `staging.env` or `production.env`. Authenticate with Basic
username `calorify` and that password. A restart or redeployment is required
after adding or rotating the value.

Keep the route behind HTTPS. Responses are marked `no-store`, omit referrers,
and use a restrictive Content Security Policy.

The fixed Basic-auth username is not a user identity or authorization layer;
the password is an operator secret controlling access to all records in that
environment. Staging and production must use independent values.

The page applies its route-specific request limit in addition to the global
limit. Every stored value is escaped before HTML rendering.

## Reading the flow

Entries are newest first and limited to ten per page. Use the All, Text, and
Image filters to narrow the view. Open a session and read its timeline from top
to bottom. Each step distinguishes generated data from a skipped or unreached
layer, summarizes its output, explains what happened next, and exposes the raw
JSON on demand. The latest streamed response is highlighted separately. Rows
created before response capture use the persisted legacy result.

Image cards reconstruct the authenticated client download URL from the stored
object key. The page never reads or displays the backend-only upload credential.

## Execution observability

New analyses include one expandable API-pass card for every initial analysis,
clarification, resume, meal-type continuation, and reanalysis request. Each card
shows:

- the ordered stream events and their elapsed offsets;
- LLM, USDA, and database operation counts plus the internal timing waterfall;
- every provider/model attempt, including failures and failover duration;
- the validated structured decomposition generated by the model;
- each selected USDA row (FDC ID, description, source type, dataset version,
  match score/margin, lookup inputs, and per-100g nutrition), an explicit
  unmatched decision, or deterministic/LLM fallback nutrition;
- the structured deterministic input to presentation enrichment and its
  generated quantity, tip, and health output; and
- clarification, meal-type, feedback, correction, and meal-log audit records.

Rows created before the observation migration still show their durable flow
snapshots but display a notice where execution detail is unavailable.

Trace persistence is allow-listed and sanitized. It does not store raw prompts,
provider messages, hidden reasoning, credentials, signed image URLs, or the
full USDA candidate set. The selected USDA decision and validated structured
outputs are retained because those are the reviewable pipeline boundaries.

## Deployment and verification

1. Deploy the backend image containing the route and its session-response,
   recent-ordering, and observation migrations.
2. Set a long unique `ANALYSIS_HISTORY_PASSWORD` in the target server's ignored
   runtime environment file.
3. Restart or redeploy that backend environment.
4. Open `/analysis-history` through HTTPS using Basic username `calorify`.
5. Confirm recent-first pagination, text/image filters, image previews, durable
   layers, latest response, observations, provider attempts, USDA selection,
   and presentation boundaries for a newly executed analysis.
6. Confirm missing configuration returns `404`, invalid credentials return
   `401`, successful responses are `no-store`, and stored markup is escaped.

Changing the password requires only a runtime configuration update and
restart; no database change is required. General backend environment handling
and release/rollback procedures remain canonical in
[`DEPLOYMENT.md`](../DEPLOYMENT.md).
