# Meal-image uploads

Meal photos are converted to WebP on the phone and uploaded through the
authenticated Calorify backend. The Oracle write credential is backend-only;
the app receives an opaque read URL and submits it to the existing image
analysis endpoint.

## Flow

```text
Flutter app
  -> single-pass WebP conversion and local 1 MiB check
  -> POST /api/v2/food/image-upload with Firebase token and raw WebP
  -> authenticate and rate-limit before body parsing
  -> validate bounded static WebP
  -> PUT to Oracle through the backend-only write PAR
  -> return an opaque shared-read-PAR imageUrl
  -> POST /api/v2/food/analyze-image with analysisId and imageUrl
```

The phone upload call is implemented in
[`food_repository.dart`](../app/lib/core/repositories/food_repository.dart).
The route is in
[`food.ts`](../backend/src/routes/v2/food.ts), WebP validation is in
[`webpValidation.ts`](../backend/src/services/infrastructure/webpValidation.ts), and Oracle
URL/key handling is isolated in
[`objectStorage.ts`](../backend/src/services/infrastructure/objectStorage.ts).

## Upload contract

`POST /api/v2/food/image-upload` accepts:

```http
Authorization: Bearer <firebase-id-token>
Content-Type: image/webp
Content-Length: <bounded byte length>

<raw WebP bytes>
```

It returns:

```json
{
  "imageUrl": "<opaque read URL>"
}
```

The request body must be non-empty and no larger than 1 MiB. The content type
must be exactly `image/webp`. The backend accepts a structurally valid static
WebP whose width and height are each at most 4096 pixels and whose total pixel
count does not exceed 16,777,216. It rejects malformed RIFF/chunk boundaries,
animation, inconsistent canvas/frame dimensions, and multiple image frames.
Metadata chunks are allowed. Validation is structural and does not claim to
decode the compressed pixel stream.

The phone performs one compression pass. Null, empty, non-WebP, or oversized
output fails locally. It never uploads original JPEG/PNG bytes under a `.webp`
name and does not retry at lower quality.

## Authentication and admission control

Firebase authentication runs during Fastify `onRequest`, before binary body
parsing. Upload admission is then limited independently by authenticated UID
and trusted source IP:

- ten uploads per UID per minute; and
- sixty uploads per source IP per minute.

Exceeded limits return `429` before buffering the body. Counters are
process-local, reset on restart, and are independent across replicas. The
deployment uses one trusted reverse-proxy hop so the IP key reflects the
originating client address.

Invalid format returns `400` or `415`, excessive bytes return `413`, and an
Oracle upload failure returns a redacted `503`. Upstream response bodies,
credentials, Firebase tokens, and Oracle error details are never returned or
logged.

## Object identity and visibility

The backend constructs the key exclusively from verified/server-owned data:

```text
<firebase-uid>/<server-UTC-timestamp>.webp
```

The UID is encoded as one path segment and never comes from request data. The
fixed-width timestamp is generated by the backend. Timestamp-only naming has a
theoretical same-user/same-millisecond collision; this is accepted for the
current implementation.

The returned read URL is intentionally public to anyone who possesses it. The
shared read PAR permits access to known or guessed keys within its configured
scope, while object listing remains disabled. The key exposes a stable
pseudonymous UID and upload timestamp, so meal-photo URLs must not be described
as anonymous.

Staging and production use separate buckets and PAR pairs. Both configured PAR
values live only in ignored backend runtime environment files. The upload PAR
must never appear in app source, build defines, CI configuration, telemetry, or
release artifacts.

## Lifecycle and accepted limits

The current implementation deliberately has:

- no upload database record or cross-system idempotency state machine;
- no synchronous delete endpoint;
- no orphan reconciliation or interrupted-analysis cleanup;
- no content/food moderation beyond bounded WebP validation;
- no compatibility bridge for read-PAR rotation; and
- no support for old clients after revoking the former app-exposed write PAR.

Oracle lifecycle policy may clean up old objects. Revoking or rotating the read
PAR breaks historical URLs issued under the previous value. Revoking the old
client-exposed upload PAR is an operational release requirement rather than an
application migration.

Runtime variables, rotation constraints, rollback, and secret handling are
maintained in the [backend deployment runbook](../backend/DEPLOYMENT.md). The
backend configuration summary is in
[`backend/README.md`](../backend/README.md).
